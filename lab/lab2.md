## Q2 - What are `backend-store-uri` and `default-artifact-root`?

The MLflow tracking server was started using:

    uv run mlflow server --host 127.0.0.1 --port 5000 --backend-store-uri sqlite:///mlflow.db --default-artifact-root ./mlruns

`--backend-store-uri sqlite:///mlflow.db` defines where MLflow stores experiment and run metadata.

Examples of metadata include:

- experiment information
- run IDs
- parameters
- metrics
- tags
- timestamps

`--default-artifact-root ./mlruns` defines where MLflow stores artifacts generated by the runs.

Examples of artifacts include trained models and other files produced by an experiment.

Therefore, metadata describes the experiment and its runs, while artifacts are the actual files produced by the experiment.

## Q3 - Why should `mlflow.db` and `mlruns/` not be tracked by Git or DVC?

`mlflow.db` and `mlruns/` contain local MLflow tracking information and experiment artifacts.

They should not be committed to Git because they are generated experiment outputs rather than source code.

They were therefore added to `.gitignore`.

Git is used to version the source code and configuration of the project.

DVC is used in this project to version the datasets.

MLflow is responsible for tracking the experiment metadata, metrics, parameters, and model artifacts.

## Q4 - What happens the first time `mlflow.set_experiment("food11")` is called?

The training script contains:

    mlflow.set_tracking_uri("http://127.0.0.1:5000")
    mlflow.set_experiment("food11")

When `mlflow.set_experiment("food11")` was executed for the first time, the experiment did not already exist.

MLflow automatically created a new experiment named `food11`.

The following message appeared:

After that, the `food11` experiment appeared in the MLflow web interface.

## Q5 - What is the difference between a parameter and a metric? Why do metrics use `step`?

A parameter is a configuration value that is fixed for a training run.

Examples include:

- learning rate
- batch size
- number of epochs
- dataset
- model architecture

Parameters are logged once because they normally remain unchanged during the run.

A metric is a measured value produced during training or evaluation.

Examples include:

- training loss
- validation loss
- validation accuracy
- test accuracy

Metrics can change during training.

The `step` argument identifies the training step or epoch associated with each metric value. This allows MLflow to store the history of the metric and display how it changes over the epochs.

## Q7 - Which learning rate gave the best validation accuracy? Is higher always better?

Among the tested learning rates, `0.0001` produced the highest validation accuracy.

The run using:

- learning rate = `0.0001`
- batch size = `32`

reached a best validation accuracy of approximately `0.7089`.

A higher learning rate is not always better.

For example, the run using a learning rate of `0.01` achieved a final validation accuracy of only approximately `0.1442`, while the smaller learning rate of `0.0001` achieved approximately `0.7080`.

This demonstrates that the learning rate must be tuned rather than simply increased.

## Q8 - Parallel Coordinates Plot

The MLflow Parallel Coordinates Plot was configured using:

Parameters:

- `lr`
- `batch_size`

Metric:

- `val_accuracy`

The plot showed that the run using `lr = 0.0001` and `batch_size = 32` achieved the highest final validation accuracy, approximately `0.708`.

The runs using `lr = 0.001` produced lower final validation accuracies of approximately `0.50` for batch sizes 32 and 64.

The run using the highest learning rate, `lr = 0.01`, performed much worse, with a final validation accuracy of approximately `0.144`.

For these experiments, decreasing the learning rate improved validation performance. Changing the batch size from 32 to 64 while using `lr = 0.001` produced only a small difference in final validation accuracy.
